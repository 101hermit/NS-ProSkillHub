## 1. 新增结构

```
② 动作层   ProAction（/api/v1/conn/** · /eval/matrix/** · /kg/** · /ix/**）
                        （复用 EvalAction 的 /eval/runs、/agents、/mcp）
                               │
③ 业务层   ConnService      —— Agent × MCP 逐格探活 + 热力图数据
           MatrixService    —— 创建（笛卡尔展开）/ 执行（串行）/ 分组对比（TOPSIS）
           KnowledgeService —— 图谱重建（实体+关系）/ 查询（含场景下钻）/ 相似 / 三种导出
           InsightService   —— 六种分析方法 + 中文结论 + 报告落库
                               │
⑤ 数据持久层 ProMapper：mx_matrix · mx_cell · kg_entity · kg_relation · kg_snapshot · ix_report
                        + 沿用标准版的 23 张表 → 共 29 张
```

## 2. 四块新增的设计要点

### 2.1 ConnService（连通矩阵）

| 设计点 | 做法 | 为什么 |
| --- | --- | --- |
| 探活口径 | 任何 HTTP 响应（含 401/403）都算"通道可达" | 401 说明 TLS 与网络都通了，只是没带对 Key —— 这是"通"的信息 |
| 逐格结论 | `ok = agentOk && mcpOk`，`detail` 指出是谁不通 | 页面一句就能定位问题 |
| 热力图 | 后端压成 `{rows, cols, values[][]}`，前端用通用 `SkChart` 的 `heatmap` 类型 | 图表组件不引 ECharts，三系统共用同一个 |
| 耗时 | 每格 = Agent 探活 + MCP 探活耗时之和 | 表格里能直接看出哪个组合慢 |

### 2.2 MatrixService（三种实验）

```
创建：
  skills × agents × mcps × Σ(paramGrid) × cases  → 笛卡尔展开成 planned_cells
  单次上限 120（超出直接 400 并告诉你"减少哪个维度"）
  (c) SKILL_COMPARE 会强制"单 Agent + 单参数"（分组对比才有意义）
  cases 为空 → 服务端按场景自拟 auto-1/auto-2(/auto-3)

执行（串行）：
  for cell in cells:
      组装系统提示 → 可选 MCP 取上下文 → AgentPort.invoke
      → 9 项指标打分（与标准版同一套口径）→ 落 mx_cell
  矩阵状态：全成功 DONE / 部分成功 PARTIAL / 全失败 FAILED
  最后算 summary（均值/最值/标准差/直方图）并落 mx_matrix.summary_json

对比：
  按 skill / agent / params 三组聚合 → 每组算 avg_score / success_rate / latency_efficiency
  → 三准则 TOPSIS（权重 3/2/1）→ 排名 → 中文结论
```

**为什么串行**：内网共享模型时，并发会让"谁慢"这件事无法归因。
串行 + 每格独立计时 = 结果可复现、耗时可解释。

### 2.3 KnowledgeService（图谱）

| 实体类型 | 来源 | 数量级 |
| --- | --- | --- |
| `SKILL` | Skill 库（375） | 375 |
| `CAPABILITY` | 8 个工程类分类 | 8 |
| `SCENE` | 6 个行业分类 + 6 个场景节点 | 12 |
| `TAG` | 所有 Skill 的标签去重 | ~230 |
| `AGENT` / `MCP` | 接入注册表 | 4 + 2 |

| 关系 | 生成规则 |
| --- | --- |
| `BELONGS_TO` | Skill → 它的分类 |
| `IN_SCENE` | Skill → 它的场景 |
| `HAS_TAG` | Skill → 每个标签 |
| `SIMILAR_TO` | 同分类且共享标签的两个 Skill（权重 = 共享标签数；最多 6000 对） |
| `EVALUATED_BY` | Skill → 实测过的 Agent |

**关键实现细节**：
1. **唯一键去重**：`kg_relation` 上有 `(src_code, dst_code, relation_type)` 唯一键，
   重建前必须按这三元组去重（实测踩过：同一 tag 在一批里重复出现会 5001）。
2. **场景下钻**：不是简单过滤节点，而是保留"该场景的 Skill + 该场景节点 + 与它们相连的一切"。
3. **布局在浏览器**：环形初始化 + 60 轮弹簧松弛，纯 `computed`，不用任何图库。
4. **导出**：CSV 会把逗号转空格避免歧义；GraphML 带 `type/name/weight` 三个 key。

### 2.4 InsightService（知识级分析）

| 方法 | 数据来源 | 算法要点 |
| --- | --- | --- |
| `DESCRIBE` | 所有 DONE 单元的 `score_total` | `Metrics.summary` + 6 桶直方图 |
| `HYPOTHESIS` | 按 `groupBy`（agent/skill/params）分组 | Welch t（不等方差）+ Cohen's d；**只有 1 组时按用例回退** |
| `TOPSIS` | 每组的均值与稳定性 | 两准则（均值 3 / 稳定性 1） |
| `CLUSTER` | 全部分数 | k-means（k=2..3），30 轮或收敛即停 |
| `REGRESSION` | `(latency, score)` 对 | 一元最小二乘 + R² |
| `AHP` | 预置 3×3 判断矩阵 | 几何平均法求权重 + CI/RI 一致性比率 |

**p 值实现**：正态近似 + Edgeworth 修正（含 Abramowitz–Stegun 误差函数近似，精度 ~1e-7）。
**为什么不用 Apache Commons Math**：多一个 2 MB 依赖，而站内只需要一个双侧 t 尾概率。

## 3. 关键设计决策

| 决策 | 理由 | 代价 |
| --- | --- | --- |
| **矩阵串行执行** | 共享模型时并发无法归因 | 48 格真实模型约 1-3 分钟 |
| **单元数上限 120** | 防误点打满模型 | 超大实验要拆几次 |
| **图谱用关系表 + 内存算法** | 不引图数据库，符合"只用 H2/MySQL"的硬约束 | 深链查询要自己在内存里做 |
| **相似度基于标签共享** | 可解释（能说出"共享哪些标签"）、无需 embedding 服务 | 语义相似但标签不同的 Skill 连不上 |
| **p 值用近似实现** | 少一个依赖；只用于"显著/不显著"的判断 | 样本 <10 时结论仅供参考（已登记） |
| **离线桩参与矩阵** | 断网时也能验证整条链路 | 离线分数与真实模型分数不可直接比（页面标 offline） |
| **分组对比固定三准则** | 页面上一眼看懂；可解释优先于"更全面" | 想加准则要改代码 |

## 4. 性能预算与实测

| 场景 | 目标 | 实测 |
| --- | --- | --- |
| 首次启动（29 表 + 375 Skill + 种子） | ≤ 35 s | **~18 s** |
| 连通矩阵（4 Agent × 2 MCP，离线桩） | ≤ 3 s | ~0.2 s（真实模型约 8×2s） |
| 矩阵执行（4 单元，离线桩） | ≤ 3 s | ~0.3 s |
| 知识图谱重建（375 Skill → 639 实体 / 719 关系） | ≤ 8 s | ~2.5 s |
| 图谱查询（80 节点） | ≤ 500 ms | ~150 ms |
| 分析（DESCRIBE / HYPOTHESIS） | ≤ 1 s | ~120 ms |
| 首屏 JS | ≤ 1 MB | **263 KB** |
